# Isolated Envelope Benchmarks

This is benchmark tooling, not a new FWS transport or supervisor implementation.
The production supervisor remains unchanged. Python FWS and Ferrous share the
candidate schemas here; the standalone Rust executable is an independent client
and server, not the production Ferrous runtime.

## Setup

Requires `flatc` 25.12.19, `capnp` 1.5.0, Cargo and Python. Termux provides both
schema compilers. Install bindings only in the isolated venv; clear inherited
harness `PYTHONPATH` when using pip. pycapnp may need a native source build.

```sh
python -m venv .external/uds-codecs-venv
env -u PYTHONPATH .external/uds-codecs-venv/bin/python -m pip install -r scripts/uds_bench/requirements.txt
mkdir -p .external/uds-generated
flatc --python -o .external/uds-generated scripts/uds_bench/schemas/envelope.fbs
cargo build --release --locked --manifest-path scripts/uds_bench/rust/Cargo.toml
```

Rust bindings are generated by `build.rs` into Cargo's build tree. pycapnp loads
the same `.capnp` schema using its native schema loader. No generated sources,
venv or compiled binaries need to be checked in. The standalone crate lockfile
pins its dependency graph. Preserve build caches.

## Checks And Runs

Resolve `BINARY` using the actual Cargo target directory (including an inherited
`CARGO_TARGET_DIR`), not an assumed repo-local `target/` path.

```sh
export FWS_BENCH_RUST_BINARY="$BINARY"
env -u PYTHONPATH .external/uds-codecs-venv/bin/python -m unittest tests.test_uds_candidate_codecs tests.test_uds_envelope_bench -v
basedpyright scripts/uds_bench/codecs.py scripts/uds_bench/run.py tests/test_uds_candidate_codecs.py
cargo test --locked --manifest-path scripts/uds_bench/rust/Cargo.toml
cargo clippy --locked --manifest-path scripts/uds_bench/rust/Cargo.toml --all-targets -- -D warnings

.external/uds-codecs-venv/bin/python -I scripts/uds_bench/run.py \
  --rust-binary "$BINARY" --rust-profile release --requests 300 --repeats 3 \
  --output .external/bench-results/uds-candidates.jsonl
```

Output uses exclusive creation. Do not overwrite earlier evidence. Finish all
builds/tests before timing. The matrix is raw/JSON-base64/msgspec-JSON-base64/FlatBuffers/Cap'n Proto,
128 B/4 KiB/32 KiB, 1/8/24 sessions, and all four Python/Rust client/server pairs.
Both peers are separate processes. Python uses standard asyncio; Rust uses a
single-thread Tokio runtime. Every session permits one outstanding request;
24-session tests are not a claim about the prototype supervisor's 16-session cap.

JSON and binary candidates carry the same version, operation, generation, stream,
offset and opaque payload fields. Integers include values above 2^53. Raw mode
carries payload only. For payloads at least eight bytes, the first eight encode
the request sequence in every codec; every response must equal its expected
bytes and metadata. Empty/small payloads are correctness probes, not sequence
probes. Endpoints decode/re-encode each envelope; there is no echo-byte shortcut.
Warmup, startup and schema loading are outside timing. All candidates allocate
fresh builders/envelopes and return owned payload bytes, not zero-copy views.

Each frame uses the same four-byte big-endian length prefix and 64 KiB cap.
Cap'n Proto uses normal **unpacked** serialization, not its compression or RPC
runtime. Payloads are opaque: inner JSON/MessagePack is not decoded by the peer.

## Limits Of This Evidence

- Python FlatBuffers is pure Python; pycapnp wraps native C++. This is an actual
  binding comparison, not a claim that either wire format is intrinsically faster.
- Python's generated FlatBuffers API lacks Rust's full verifier. The adapter
  checks identifier, operation, required payload and vector bounds; bulk copying
  uses the pinned generated layout/runtime accessor instead of a per-byte loop
  or adding NumPy. It is **not** a production hostile-input verifier. Rust verifies
  FlatBuffers roots; Cap'n Proto readers use traversal/depth limits. Validation
  work is consequently not identical, and this must accompany timing conclusions.
- The new JSON control has matching metadata. The earlier
  `bench_uds_envelope.py` JSON control has only op/data and is not interchangeable.
- `json-msgspec` changes the Python encoder/decoder, retaining the same manual
  field validation and byte-identical JSON/base64 wire shape. Rust continues to
  use serde_json for both JSON labels; this is not a Rust msgspec implementation.
  This control does not measure an optimized msgspec Struct schema.
- Codec-only results currently cover Python encode/decode/equality, not Rust
  codec-only or allocation profiles. Transport metrics include client CPU,
  useful/wire bytes, RPS, RTT percentiles and standard deviation. Server CPU/RSS,
  fixed offered load and detailed jitter attribution remain future work.
- These are transport-only probes, not existing JSON-RPC workload benchmarks.
  No authentication, raw log writing, reconnect, replay or supervisor topology is
  included. Do not subtract timings to invent production overhead estimates.
- Thermal conditions and unrelated device workload remain uncontrolled. Repeated
  randomized trials reduce order bias but do not establish a performance ceiling.

Neither candidate is selected for production by these tests alone. Next compare
existing application RPC/notification workloads with matched direct-pipe and
actual supervisor controls, then complete adversarial validation and packaging.

## Actual Native Pipe / Supervisor RPC

`rpc.py` runs the existing Rust `fws-pipe-jsonrpc-bench-server` unchanged as the
child for every lane. Python encodes requests and decodes final JSON-RPC payloads
with msgspec. Protocol framing and response/notification routing stay in the
benchmark consumer, not FWS. The original supervisor controls use msgspec on
the Python side; shared-client lanes use stdlib JSON (fallback) or Rust serde_json
(native). Authentication setup is outside timing. The supervisor remains JSON/base64, not FlatBuffers or
Cap'n Proto. Those candidate codecs are still transport-only probes above.

Install runtime dependencies only into the benchmark venv, then build native
artifacts without staging anything into the FWS package or changing an install:

```sh
env -u PYTHONPATH .external/uds-codecs-venv/bin/python -m pip install -r scripts/uds_bench/requirements-rpc.txt
PYO3_BUILD_EXTENSION_MODULE=1 PYO3_PYTHON="$PWD/.external/uds-codecs-venv/bin/python" \
  cargo build --release --manifest-path native/fws_pipe_pump/Cargo.toml --lib --bin fws-pipe-jsonrpc-bench-server
cargo build --release --manifest-path .external/ferrous-framework/crates/fws-supervisor/Cargo.toml --bin fws-supervisor
PYO3_BUILD_EXTENSION_MODULE=1 PYO3_PYTHON="$PWD/.external/uds-codecs-venv/bin/python" \
  cargo build --release --manifest-path native/fws_supervisor_client/Cargo.toml
```

Resolve the actual target directory via Cargo (including `CARGO_TARGET_DIR`).
Copy its `libfws_pipe_pump.so` to `.external/uds-native/fws_pipe_pump.so`, retaining
the cached original and existing package artifacts. Use the interpreter-correct
ABI/build settings; do not rename a different interpreter's extension to fake ABI
compatibility. These commands were checked on regular CPython 3.14.6 on Termux.

```sh
FWS_SUPERVISOR_CLIENT_EXTENSION="$PWD/.external/uds-native/fws_supervisor_client.so" \
 .external/uds-codecs-venv/bin/python -I scripts/uds_bench/rpc.py \
  --child "$TARGET/release/fws-pipe-jsonrpc-bench-server" \
  --supervisor "$TARGET/release/fws-supervisor" \
  --native .external/uds-native/fws_pipe_pump.so \
  --requests 1000 --repeats 5 \
  --output .external/bench-results/uds-rpc-msgspec.jsonl
```

Also stage the matching `libfws_supervisor_client.so` into the ignored directory
as `fws_supervisor_client.so`. This binding is optional for production and required
for the explicit native benchmark lane. No package installation is involved.

The six lanes are (use `--lanes` to select an explicit subset):

- `native-default`: real FWS manager, `native_pipe_testing`, default read/log settings.
- `native-matched`: same manager, 8 KiB native reads and immediate flush settings
  using existing launch parameters, matching supervisor read size/visibility.
- `supervisor-asyncio`: real authenticated Rust supervisor, Python asyncio socket reads.
- `supervisor-native-reader`: same supervisor, benchmark-only handoff of the
  client UDS FD to the existing PyO3 native reader. Framing/decoding remain Python.
  Asyncio still owns writes. Prebuffer bytes and EOF are preserved; no competing
  socket readers or extra reader thread. The extension's mandatory log sink is
  `/dev/null`, so discard-write overhead is included but no outer-envelope log is
  retained. Raw child logs are written only by the supervisor.
- `supervisor-shared-python`: common experimental API, bounded asyncio reference
  client with stdlib JSON outer decoding; msgspec still decodes application bytes.
- `supervisor-shared-native`: same common API, shared Rust client through the
  API v2 PyO3 binding; authentication/framing/envelopes/ACKs/generations in Rust.
  Hot-path completion delivery uses asyncio readiness FD callbacks, no polling
  and no Python calls from Rust worker threads. Rare controls use the standard
  PyO3 async bridge. All output buffers and outstanding write counts are bounded.

The matching log contract is **raw bytes visible before delivery, no fsync**.
Implementation is not identical: native pipe uses `std::fs::File` writes;
supervisor uses Tokio file writes/flush completion and their blocking-pool work.
The test verifies raw-log length and SHA-256 against observed output while the
child is still running, before shutdown can perform a final flush. It also
requires empty stderr, exact result payloads and IDs, and exact notification
contents/order/counts. Native pipe activation must succeed; fallback fails.

Workloads: sequential RTT (128-byte response), concurrent responses (4 KiB,
eight requests in flight), and mixed (4 KiB response plus two 2 KiB notifications,
eight requests in flight). Sixteen warmup requests and launch/authentication/
shutdown are excluded. Each trial runs in a fresh process with a disposable FWS
store/secret and peer startup disabled. Trials are blocked by workload/repeat,
with shuffled lane ordering. Tests use larger fragmented responses as well.

The supervisor still serializes one outstanding control command per session.
Every input write waits for its transport ACK; direct native pipe has no such
ACK. This is an intentional measurement of the current prototype, **not an
isolated encoding-cost comparison**. RPC requests can remain in flight while
that serialized input lane proceeds. Public FWS `write_to_pipe` accepts text,
so its bytes-to-text conversion is included rather than bypassing that API.

The disposable native-pipe fixture explicitly closes the original paused asyncio
subprocess transport after manager termination to avoid an unclosed-transport
warning. This is outside timing and does not change production cleanup behavior.

Process tests require `FWS_BENCH_RPC_CHILD`, `FWS_SUPERVISOR_BINARY`,
`FWS_BENCH_NATIVE_EXTENSION`, and `FWS_SUPERVISOR_CLIENT_EXTENSION`, each pointing
to the above explicit artifacts:

```sh
env -u PYTHONPATH .external/uds-codecs-venv/bin/python -m unittest tests.test_uds_rpc_bench -v
basedpyright --pythonpath .external/uds-codecs-venv/bin/python scripts/uds_bench tests/test_uds_rpc_bench.py
```
